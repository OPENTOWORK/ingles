# RUOE vs Listening — generation architecture analysis

**Version:** v1. Analysis only. No runtime file, prompt row, or exam was changed.  
**Date:** 22 September 2026.

Production prompt rows were read with `SELECT` only, on project `ENGLISH_PROD`, table `levels_exam_part_prompt_overrides`, level `b2`. No row was updated. Full prompt bodies were not copied into this document. Comparison uses lengths, dates, and the presence or absence of distinctive sentences.

---

## 1. What actually exists

The hypothesis to test was:

- Listening: natural communicative content, then task constraints, then questions.
- RUOE: choose the target answer or structure, build the sentence around it, validate afterwards.

**Result:** neither engine is a staged pipeline in code. Both are one model call that returns the text and the items together. The quality gap comes from what that single call treats as the primary object, and from what is locked before a sentence exists.

### Listening objects that are not in the repository

Searched the repo for Speech Cards, transcript briefs, listening Task Requirements, and a listening blueprint generator. **None of these exist as files or prompts.**

Listening does not have its own Style Cards. The Style Cards in the repo (`SC-01`–`SC-06`) are RUOE editorial cards. Production listening generation does not inject them.

### What Listening generation actually is

B2 Listening is parts 10–13 of the same Cambridge generator as RUOE:

| Dralo part | Cambridge listening | Activity |
|---|---|---|
| 10 | Part 1 short extracts | `short-extracts` |
| 11 | Part 2 sentence completion | `sentence-completion` |
| 12 | Part 3 multiple matching | `multiple-matching` |
| 13 | Part 4 interview | `conversation` |

Prompt text lives in `buildExamGeneratePrompt()` in `src/lib/draloAiExamPrompts.js`, branch `mode === 'listening'`. Resolution is the same function as RUOE: `resolveEffectiveExamPartGenerationPrompt()`, and `useCodePrompts` defaults to `false`.

After the model returns JSON, `expandListeningScriptsInGenerated()` may lengthen a short script. The expansion instruction is: keep the same speakers, the same meaning, and a natural B2 exam style. It does not insert a collocation, a stem, or a transformation.

`examPartValidation.js` then checks counts, gap markers, 1–3 word answers, and option pools. There is no blind linguistic solver for Listening.

### What RUOE generation actually is

Two paths:

**Production** (`generateAndPersistLevelExamPart`):

1. Topic string from `EXAM_THEMES` or the caller. Not a Content Brief.
2. Effective prompt = database row if `user_prompt` is non-empty, else the code prompt.
3. One JSON completion: passage, items, and keys together.
4. Mechanical validation in `examPartValidation.js`.
5. Parts 1–2: `examPartQualityValidator.js` (best-letter blind solve + rubric).
6. Parts 3, 5, 6, 7: `ruoeAiAdversarialQuality.js`.
7. Part 4: deterministic checks in `ruoePart4Quality.js` when that module is invoked (pilot bundle and metadata repair). The production generate path’s extra AI review does not include Part 4.

**Local pilot** (`ruoePilotRegeneration.js`), not the production default:

1. Approved Content Brief JSON (hand-approved, not generated by a model in this repo).
2. Style Card text appended.
3. `BRITISH_ENGLISH_BLOCK` appended. This block is **not** in the production rows (checked: the sentence “Think and write in natural British English” is absent from every B2 override).
4. Same one-shot generator.
5. Local repairs, then the validation bundle.
6. Part 4 only: `generatePilotPart4FromBlueprint()` prepends an approved blueprint and the policy “Keep family_id, keyword, target_structure, difficulty_band per slot. Generate NEW sentences and answers.”

Content Briefs are inputs (`DRALO_RUOE_12_Content_Briefs_Pilot_v1_0_APPROVED.json` and later batches). There is no runtime prompt that creates them. Production parts 1–5 and 7 do not mention “Content Brief” in the stored user prompt. **Part 6 does**, because Architecture v2 is inside that prompt.

## 2. Side-by-side generation order

| Step | RUOE production (parts 1–7) | Listening production (parts 10–13) |
|---|---|---|
| 1 | Optional topic string | Same |
| 2 | DB user prompt wins | Same |
| 3 | System line: “Output only valid JSON for one complete B2 First exam part.” (59 characters; matches code) | Same system line |
| 4 | One completion writes the article **and** the keyed items | One completion writes the script **and** the questions |
| 5 | No second pass that starts from finished prose, except Part 6’s *instruction* to draft ungapped first (still inside the same call) | If the script is short, expand it and keep meaning |
| 6 | Structural validator, then a linguistic judge for some parts | Structural validator only |
| 7 | Repairs, where they exist, replace a stem, a Part 4 item, a Part 7 stem, or a Part 5 length | Repair only lengthens speech |

Listening is closer to “speak first” **inside the prompt’s priorities**, not because the code runs a later question-writing stage. RUOE parts 1–4 are closer to “item and text in one breath, with the test point specified up front.” Part 6 is the RUOE prompt that actually describes content-first order, and it is not one of the parts that keep failing in the way Parts 1–4 do.

## 4. Target-first points, from the implementation

### Part 1 — multiple-choice cloze

There is no code step that (a) chooses a collocation, (b) writes four options, then (c) writes the sentence. There is also no code step that writes a finished paragraph and only afterwards picks a gap.

The live prompt’s order inside the one call is:

1. Passage shape, word count, “authentic B2-level British English.”
2. “The correct choice is decided by meaning, collocation, dependent preposition, word partnership or lexical precision.”
3. Four one-word options. Distractors fail on that partnership.
4. A quota of knowledge types across the eight items (in the current file; the stored row was not fully diffed for every quota).

So the model is told to produce a natural article **and** to make each gap solvable only by a lexical partnership, with three near neighbours that fail. That is target-aware writing. The validator afterwards asks for the **best** letter (`blindSolve`), not for four independent sentence judgements. One rival that is still natural can survive if the solver prefers the key and does not volunteer the rival.

### Part 2 — open cloze

No function writes a continuous text and then deletes eight function words.

The prompt requires a mix of articles, auxiliaries, prepositions, relatives, and so on, and the passage must already contain gaps `(9)`–`(16)`. The uniqueness test is a checklist in that same prompt, not a later independent pass over candidate words. A grammar shopping list plus eight gaps is pressure to place targets, even though the prompt also says the completed text must sound natural.

### Part 3 — word formation

The prompt does say “Natural sentence first, transformation second.” The schema still returns `stem` and `answer` together, and the quotas still demand less-transparent derivatives, a negative or privative form, and class changes.

`repairPart3NoTransformItems()` does not rewrite the sentence from scratch. It asks for a **new stem and derived answer for the same gap context**. That preserves the gap and hunts a derivation.

A phrase such as “these actions are not powerless” fits this pressure: a negative derivation is required somewhere in the eight items, and the sentence is allowed to host it. The repository does not contain that exact sentence. The path that would produce it does exist.

There is no check that the answer is a direct derivation of the stem with no extra lexeme. `DECIDE → decision-making` would not be rejected by “stem must differ from answer.” `making` is a second word, and the one-word mechanical check would catch a two-word answer, but a single token that smuggles an extra idea is not a named rule.

### Part 4 — key word transformations

**Production prompt:** naturalness is stated first, then the model must also emit `family_id`, `target_structure`, a 2–5 word answer, and two marking points. Mechanics and sentences are one object. A grammatical, keyword-preserving answer can satisfy the schema while the completed sentence 2 shifts certainty, time, or agency. `detectPart4AlternativeRoutes()` only catches a few keyword patterns (`WISH` / `REGRET` / short `MUST`). It does not compare propositions.

**Pilot blueprint path:** this one **is** target-first in code. The slot already has `family_id`, keyword, and `target_structure`. The instruction is to keep those and write new sentences. Word count and keyword checks can pass after that. Semantic identity is a prompt checklist (“MEANING IDENTITY”) in the current file, not a separate judge that can fail the item while mechanics pass.

`regeneratePart4Item()` builds a new item from a topic and a partition example. It does not start from two finished natural sentences.

## 5. Why Listening transcripts come out more natural

Only differences present in the repository:

| Difference | In the repo? | Can it explain the gap? | Safe to adapt to RUOE? |
|---|---|---|---|
| The primary object is a speech event (conversation, interview, monologue) with contractions, hedging, interruptions. Questions are tests of that event. | Yes. Listening prompts, parts 10–13. | **Yes.** The model is not told that each sentence exists to host one collocation, stem, or transformation family. | Yes, as an order of work for Parts 1–3: finished prose before gaps. Not by copying spoken-register rules into articles. |
| No Content Brief, Style Card, or blueprint is injected on the production listening path. | Yes. Stored listening prompts do not mention them. | **Partly.** Fewer locked editorial targets. ## 6. Direct answer

Listening does **not** run a separate “transcript, then questions” program. It wins on naturalness because the prompt’s job is to write speech that could be said, and the exam questions are constraints on that speech. It does not choose a single lexical key and then construct the sentence to fit it.

RUOE parts 1–4 do not have a coded “target, then sentence” function either, except Part 4’s pilot blueprint. They still behave that way because one prompt both demands the linguistic target (partnership, grammar category, derivation quota, transformation family, keyword, word count) and asks for natural British English in the same breath. When those conflict, nothing in the live path discards the target. Validation then checks the machinery, or asks which option is best, and a mechanical pass can hide a semantic or collocation failure.
